# Claude Code mod——STATE の注入、プロンプト上の帯、フライトログ、tripwire、ロールガード

> English:[mod.md](mod.md) · 繁體中文:[mod.zh-TW.md](mod.zh-TW.md) · 简体中文:[mod.zh-CN.md](mod.zh-CN.md)

**オプトインのアドオン。Claude Code 専用。** `init` が黙ってインストールすることはない。

## これは何か

`flightwake-mod` は、関数 hook でできた Claude Code のプラグイン(「mod」)。Codex と Gemini CLI には同等のものがない。
flightwake のそれ以外のすべて(skill、Stop hook、下部ゲージ)は、mod があってもなくても同じように動く。
真実の源はこれまでどおり `.flightwake/` の Markdown 1 つだけ。

mod が読むのは次のもの:

- `.flightwake/`
- git の状態(常に `git --no-optional-locks` で読むので、`.git/index` を書き換えることはない)
- CLAUDE.md / .claude/CLAUDE.md / CLAUDE.local.md の flightwake / roles マーカーブロック
- AGENTS.md / GEMINI.md の flightwake マーカー(言語の取得だけ)
- `package.json` の scripts
- 実際に有効な `statusLine` 設定
- `spend` 用:このセッション自身の `~/.claude/projects/` 配下の transcript(トークンの集計だけ)
- `fleet` 用:`<base>/sessions/*.json` のセッションファイル(下の「セッション状態の報告」を参照)、ほかのセッションの `~/.claude/projects/` 配下の transcript がまだあるか(存在の確認だけ。そのセッション自身の transcript のパスに限る)、`<base>` が記録フォルダーか git リポジトリ内か(`<base>/STATE.md` と、`<base>` とその上の各フォルダーの `.git` と `.flightwake/STATE.md`。存在の確認だけ)、repo のルートと `<base>/sessions` が実際にどこに着くか(リンクをたどる `stat`)
- `tripwire` の一致回数用:`<base>/trips` とこのセッション自身のファイルに対する同じ確認
- `panel` 用(Orca の中だけ):Orca のターミナル一覧(`orca` CLI 経由)と、一覧にある各 repo の `.flightwake/STATE.md` および指示ファイルのマーカー(読み取りのみ)

ネットワークは使わない。repo の中にも、あなたの記録(STATE / DECISIONS / TRAPS / records / ROLES.md)にも**決して書き込まない**。
mod 自身が持つ状態は session ごとのもの(`$.state`)で、例外は 2 つ:**ファイルへの書き込みは、対話セッションごとに 2 つ、どちらも repo の外の
`<base>` の下だけ**——`<base>/sessions/<id>.json`(`fleet` 機能)と `<base>/trips/<id>.json`(`tripwire` 機能の一致回数)。`<base>` は絶対パスの `FLIGHTWAKE_HOME`、なければ `~/.flightwake`。もう 1 つは `panel` 機能で、サイドパネルを最後に開いたか閉じたかという「はい / いいえ」を 1 つ、mod 自身の Claude Code プラグインストアに持つ。`<base>` が session の
repo の中に解決されるとき、flightwake の記録フォルダーのとき、どこかの git リポジトリ内にあるときは、どちらのファイルも書かない。mod の中で起きたエラーは黙って無害化される。
`.flightwake/STATE.md` のないフォルダーでは、何もしない。表示言語は、インストール時に指示ファイルのマーカーへ記録された言語に従う。

## 読み込まれる条件

次の条件がすべてそろったときだけ、mod は読み込まれる:

- Claude Code **2.1.287 以降**。
- Claude Code はプロジェクトの `.claude/skills/flightwake-mod/` から、`flightwake-mod@skills-dir` として読み込む。
  ただし、そのフォルダーのワークスペース信頼プロンプト(初めて開いたときに出る)を承認した後に限る。
- session を **repo のルート**から始めたとき。サブディレクトリから始めると読み込まれない。

個人ディレクトリに同名のプラグインがあると、プロジェクトのものより優先される。

## インストール、更新、削除

```bash
npx flightwake setup           # アドオン一覧の 2 行目。Claude Code を選ぶと表示され、既定で選択(*)
npx flightwake init --mod      # 直接インストールする
npx flightwake update --mod    # 既存のインストールに追加する(ほかのオプションはそのまま)
npx flightwake update          # すでに入っている場所だけ refresh する
npx flightwake uninstall       # 配布したファイルだけ削除(自分で足したファイルは残る)
```

- **`setup`**:アドオンは 1 つの一覧で選ぶ(Enter = `*` の行、番号 = その番号だけ、`0` = なし)。Claude Code を選ぶと
  mod は 2 行目に `*` 付きで表示され、平易な言葉で説明する:Claude Code 2.1.287 以上が必要;repo のルートから起動した
  セッションで、フォルダの信頼(trust)を承認すると読み込まれる;開いたままのセッションは再起動が必要。`claude --version`
  がそれより古いバージョンを返すと、その旨を表示して既定では選択しない。バージョンが読めない(`claude` がない、または
  5 秒以内に応答しない)ときは選択したままにする。
- **`init --mod`**:インストールする。Claude Code が設定対象の agent に含まれていなければ、メモを表示して mod をスキップする
  (エラーではない)。フォルダーが既にあれば、`--force` を付けない限りスキップする。
- **コピーされるもの**:プラグインのマニフェスト(`.claude-plugin/plugin.json`)、`hooks/`、`types/`。
  テストと開発用スクリプトは含まれない。
- **`update`(と `init --force`)**:mod がすでにインストールされている場所だけ、ファイルごとに refresh する。
  `.claude/skills/flightwake-mod/` の中にあなたが足したファイルは残る。素の `update` が mod を新たに追加することはない。
  `update --mod`(またはインストール済みの repo で setup →「更新してアドオンを追加」)なら追加し、ほかのオプションは
  そのまま。Claude Code を選んでいて mod が未インストールなら、`update` と `init` は最後に 1 行でそれを知らせる。
  誰かが求めるまで何も追加しない(出力には「追加する前に使う人に確認を」と agent 向けに明記してある)。
- **`uninstall`**:flightwake がここに配布したファイルと、それで空になったフォルダーだけを削除する。`.claude/skills/flightwake-mod/` のそれ以外(自分で足したファイル、Claude Code が書いたファイル)は残し、出力に一覧を出す。flightwake がファイルを配布した位置がディレクトリになっている場合も、そのまま残して一覧に出し、再帰的に削除することはない。`uninstall --purge` は `.flightwake/` だけが対象で、これらも削除しない。
- **`--private`**:mod のフォルダーは `.git/info/exclude` のブロックに入る。フォルダーが既に git で追跡されている場合、
  `--private` は何も書き込む前に拒否する(ほかの private の要件と同じ)。private のインストールに後から `update --mod` で
  mod を足した場合は、private のまま exclude ブロックに加えられる。

### doctor

`npx flightwake doctor` は mod がインストールされているかを報告する(任意の項目なので、未インストールは問題ではない)。
インストールされているときは次を検査する:

- マニフェストが存在し、解析できる
- `hooks/hooks.json` と、そこで名前が挙がっているモジュールが存在する
- 配布されるファイルがすべてそろっている
- インストール済みのバージョンが、パッケージ内のものと一致する(不一致は warning で、`update` を案内する)
- 配布ファイルが手で編集されている(warning;`update` で元に戻る)
- `claude --version` が実行できれば 2.1.287 と比較する(古ければ warning;読み取れなければヒントを出すだけで、失敗にはしない)

doctor には、フォルダーが信頼済みかどうかも、session が repo のルートから始まっているかも見えない——その旨を doctor 自身が表示する。
mod が読み込まれたかどうかは Claude Code の中で `/fw-mod` を実行して確認すること。

## 8 つの機能

機能ごとに専用のスイッチがある(プラグインのオプション。7 つは既定でオン、ロールガードは既定でオフ)。サイドパネルのスイッチは `/fw-panel` を使えるようにするだけで、頼まれない限りパネル自体は開かない。

| スイッチ | 既定 | 何をするか |
|---|---|---|
| `stateInject` | オン | session 開始時に、`.flightwake/STATE.md`(session ごとに 1 回取ったスナップショット)をシステムプロンプトに加える。「これは前回の締めの時点の状態であり、git も確認すること」という注記つき。未記入のテンプレート STATE の場合は、代わりに「コールドスタートを実行する」という 1 行を入れる。6000 文字を超えるときは、先頭の N 文字を切り取るのではなく、frontmatter、「進行中」と「次の入口」のセクション、ファイルパスを入れ、STATE を圧縮するよう促す。`fw-coldstart` の代わりにはならない(遅れの確認と最新 record の読み込みは、これまでどおり skill の仕事)。 |
| `band` | オン | プロンプトの上に 1 行:health の色、STATE の遅れ(Stop hook の検査と同じ数え方。bot の commit は数えない)、コンテキスト使用率、トークンとコスト(`spend` 参照)、次に勧めるコマンド。下部ゲージ(`statusline.mjs`)が実際のステータス行になっていないときは、帯は**常に表示**され、Claude Code がコンテキスト使用率を報告していれば**常にそれを表示**する——60% になるのを待たず、すべて順調でも消えない。ゲージの代わりをする。色のしきい値は変わらない(60% 以上で黄、80% 以上で赤)。STATE が未記入のテンプレートのままなら、health は `?` と表示され、「STATE が未初期化——まず /fw-coldstart」というヒントが出る。コンテキストが 80% に達したときは toast を 1 回出す。ゲージが実際のステータス行になっているときは、帯はゲージがすでに表示している項目を隠して静かにし、toast だけが残る。 |
| `recorder` | オン | session のフライトログ:変更されたファイル(agent のツールが報告したもの、およびシェルコマンドから推定したもの。後者は別の節に分けて表示)、commit、認識できたテストコマンドとその結果。時刻はローカル時刻(UTC オフセットつき)と UTC で表示する。`/fw-log` がそれを出力し、`fw-record` が `tests:` の証拠と変更一覧に使う。record を書き込むことはない。 |
| `tripwire` | オン | agent がファイルを編集したとき、またはコマンドを実行したときに、有効な TRAPS エントリの任意フィールド `paths` / `commands` に一致すると、そのエントリの要旨と確信度を、session ごとに 1 回だけ agent に見せる——ツールの実行**後**に(守るのは次の試行であって、今回のものではない)。ブロックはしない。`probable` / `suspected` のエントリは、結論ではなく手がかりとして表示される。 |
| `roleGuard` | オフ | このフォルダーの Claude の席のロールについて、ロール本文(ROLES.md)の `deny-write: [globs]` 行が、メイン session による該当パスへの `Edit` / `Write` / `NotebookEdit` のブロックになる。メッセージには、ロール名、ルール、代わりにどうするかが示される。この session について解除できるのは本人だけで、プロンプトに自分で `/fw-role-release` と入力する。解除はステータス行に表示され続ける。詳細は [roles.ja.md](roles.ja.md) の「オプション:Claude Code mod のロールガード」を参照。 |
| `spend` | オン | このセッションで使ったトークン数と、API 定価換算のコスト。金額は Claude Code 自身の台帳(`/cost` と同じ、API 定価換算。サブスクリプションでは請求ではない)。トークンは `~/.claude/projects/` 配下のセッション transcript から、API 応答 1 件につき 1 回だけ集計(サブエージェントは別 transcript のため含まない)。band の末尾の欄(`1.2M tok · ≈$4.99`)——下部ゲージが実際のステータス行のときはゲージが同じ欄を表示し band は沈黙——と `/fw-mod` の 1 行に表示。`/fw-cost` が内訳(キャッシュ外入力 / キャッシュ書き込み / キャッシュ読み取り / 出力)を表示。各ターン後に更新。 |
| `fleet` | オン | このセッションの状態——作業中、応答待ち、待機、終了——を repo の外の `<base>/sessions/<id>.json` に報告する。`/fw-fleet`、`npx flightwake fleet`、下部ゲージの `⛔` 欄が使い、セッションが予期せず止まった後には `claude --resume` のヒントを 1 回出す。対話セッションのみ。プロンプトやコマンドの内容は決して書かない。下の「セッション状態の報告」を参照。 |
| `panel` | オン | `/fw-panel` が transcript の横にペインを開く:この repo(health、遅れ、コンテキストバー、コスト、注意が要ること、STATE の「進行中」と「次の入口」)と fleet 全体——Orca の中ではすべてのエージェントのターミナル(Claude Code と Codex)を repo ごとに並べ、**移動** ボタンと確認つきの **締め** ボタンが付く。頼んだときだけ開く。一度開くと、閉じるまで以後のセッションで自動的に再び開く。下の「サイドパネル」を参照。 |

### スイッチの設定

スイッチは Claude Code の `/config` か、*ユーザー*設定(`~/.claude/settings.json`)に書く:

```json
{
  "pluginConfigs": {
    "flightwake-mod@skills-dir": {
      "options": { "roleGuard": true, "band": false }
    }
  }
}
```

プラグインのオプションはプロジェクト設定からは読まれない。そのためインストーラーが代わりに設定することはできず、各自の選択になる。

### tripwire が使う TRAPS のフィールド

どちらも任意。これらを持たない古いエントリは、単に一致の対象にならない。

```yaml
paths: ["src/db/**", "*.sql"]
commands: ["npm run migrate", "psql"]
```

- `paths`:repo 相対の glob。`/` を含まないパターンは、どの深さでもそのファイル名に一致する。
- `commands`:コマンドの先頭部分(プレフィックス)で、トークンごとに比較する。正規表現は使えない。
- superseded になったエントリは、決して一致の対象にならない。

**一致回数の記録。** エントリに一致したツール呼び出しは、すべて数える——「session ごとに 1 回」のヒントが黙っている 2 回目以降も含めて。エントリ名ごとに回数と最初・最後の時刻を、
repo の外の `<base>/trips/<session id>.json` に書く。`<base>` と書き込みを断る規則はセッション状態の報告ファイルと同じ(repo の中、記録フォルダー、どこかの git リポジトリの中には書かない。
シンボリックリンク越しには書かない。自分のものでないファイルは上書きしない)。対話セッションだけで、一致した呼び出しのたびにファイル全体を書き直す。形式は下の「trip ファイル」を参照。
これは後で TRAPS を圧縮するときの根拠になり、`npx flightwake traps stats` がファイルを合計する。数えることでブロックすることはなく、ヒントも変わらない。書き込みを断ったときや失敗したときも黙っている。
`tripwire` がオンのときだけ記録するので、記録が残るのは mod の入った Claude Code のセッションだけ——Codex、Gemini CLI、mod のない Claude Code は残さないため、合計は下限として読むこと。`/clear` の後は新しいファイルになる。

### 何をしているかを確認する:`/fw-mod`

`/fw-mod` は読み取り専用のコマンド。8 つの機能それぞれについて、オン / オフ / アイドルのいずれか、その理由、反映させる方法を一覧にする(このセッションのトークン数と API 換算コストの 1 行を含む。内訳は `/fw-cost`)。たとえば:

- 下部ゲージが検出されたので帯が隠れている。
- tripwire はオンだが、`paths` も `commands` も持つ有効な TRAPS エントリがないためアイドル。
- ロールガードがオフ(オンにする方法つき)、またはオンだが、このフォルダーの席にロールがない、あるいは `deny-write` がないためアイドル。
- STATE がこの session に注入された、または、STATE が未初期化のため「/fw-coldstart を実行する」という注記だけが入った。
- このセッションが「待機」として `~/.flightwake/sessions/…` に報告中、または `-p` 実行やフォルダーが repo 内になるため報告していない。

mod のバージョン、検出された言語とプロファイルも表示する。何も変更せず、8 つのスイッチには含まれない(flightwake がインストールされている場所ではいつでも使える)。

## サイドパネル(`panel`)

下部ゲージが有効なあいだ帯は自分を隠すので、両方を入れると mod の表示は画面から消える。サイドパネルは開いたままにしておける 1 か所で、上にこの repo、その下に fleet 全体が並ぶ。各部分はカードで描かれ、文字はペインの幅で折り返される。

- **この repo**(カードの色は health に従う):health、STATE の遅れ(帯の読み取り値。パネルが自分で数えるのは帯がオフのときだけ)、コンテキストバー(緑、60% から黄、80% から赤)、このセッションのトークンとコスト、flightwake のインストール版と mod のバージョン、そして——該当するときだけ——`!` を付けた行:コンテキストが 80% 以上(締めに入る:`/fw-record` → `/clear` → `/fw-coldstart`)、health が黄または赤の理由(STATE の `health:` の値の後ろのコメント)、作業ツリーの未コミットのファイル、STATE の `latest_record` が指す record の「未完了 / 引き継ぎ」の項目(`.flightwake/` 配下の `records/<name>.md` のみ)、有効な TRAPS エントリが 20 件超(fw-coldstart が圧縮を促す行)。
- **Fleet**——Orca の中では:Orca が持つすべてのエージェントのターミナル(Claude Code、Codex、ほかのエージェント CLI。ふつうのシェルは除く)を、repo ごとに 1 枚のカードで並べる。応答待ちのエージェントがいる repo が先頭(`⛔`、赤い枠)、次に作業中(`●`)、最後に待機中(`○`)。各カードの 1 行目は repo と、その health および flightwake のバージョンで、その repo 自身の `.flightwake/STATE.md` と指示ファイルのマーカーから読む(読み取りのみ。この repo と違うときは `≠` が付く)。エージェントごとに 1 行:エージェント、タブのタスクタイトル、席のロール、状態とその経過時間。mod 0.3.0+ を入れた Claude Code セッションは、セッション状態の報告ファイルに正確な状態、コンテキスト使用率、ロールを報告し、それが優先される。ほかのエージェントの状態は、タブのタイトル(Claude Code の `✳` / スピナー、Codex の「Action Required」)と最後に出力した時刻から読むので推測であり、パネルもそう表示する。
  - **移動**:Orca をそのタブに切り替える。
  - **締め**:待機中で、flightwake に送るコマンドがあるエージェントにだけ出る。押すとまず確認が出る(「/fw-record を送る」/「やめる」)。確定の押下では最新の一覧を取り直し、エージェントがまだ待機中のときだけ `/fw-record`(Claude Code)または `$fw-record`(Codex)を送る。Codex の `$` スキル選択がコマンドと一緒に送った Enter を取ってしまうため、パネルは入力欄を一度読み直し、そのコマンドがそのまま残っているときだけもう一度 Enter を押す。それ以外のものがほかのエージェントに入力されることは決してない。
  - Orca の外、または Orca が応答しないときは、fleet の部分が各 Claude Code セッション自身の報告に切り替わる(応答待ちが先頭、ロール付き。コンテキスト 80% 以上なら締めの行、flightwake または mod のバージョンが違うときはその行が付く)。
- **進行中 / 次:** STATE のその 2 節の最上位の項目(それぞれ最大 5 件と 6 件。超える分は「ほか n 件」の 1 行)。見出しはテンプレートの 4 言語すべてで照合し、Markdown はプレーンテキストにする。
- **このセッション:** フライトログの件数(ファイル、シェルから推定したファイル、テスト実行の回数と ✓/✗、commit)、直近のテスト実行、最近変更されたファイル。

**開閉。** `/fw-panel` で切り替える。`/fw-panel on` と `/fw-panel off` は状態を明示する。頼まれない限り開かない:一度開くと、以後のセッション(flightwake のある repo ならどこでも)は開始時に開き、閉じる——`/fw-panel`、閉じるマーク、または ctrl+x x——とそれが止まる。表示位置は Claude Code が決める:フルスクリーンのレイアウトで端末が 110 桁以上なら transcript の横、それ以外はプロンプトの上。セッション開始時に再び開こうとして端末が狭いときは、広げるか `/fw-panel` を実行するまで描画されない。端末のメイン画面(`CLAUDE_CODE_NO_FLICKER=0`、または tmux の既定)では常にプロンプトの上に開く。

**何を実行するか。** 描画中は何も実行しない。データは描画の外で集める。Orca の中(`ORCA_TERMINAL_HANDLE` が設定されている)で、ペインが開いているあいだだけ、10 秒ごとに `orca terminal list --json` を実行し(CLI は `ORCA_CLI_BIN_DIR` のもの、なければ `PATH` 上の `orca`)、一覧にある各 repo の STATE の frontmatter とマーカーは 1 分に 1 回までしか読み直さない。`orca terminal switch` と `orca terminal send` は、上に書いたとおりあなたがボタンを押したときだけ実行する。ペインを閉じるとポーリングも止まる。

## セッション状態の報告(`fleet`)

対話セッションはそれぞれ 1 つのこと——**あなたを必要としているか**——を repo の外の小さなファイルに報告する。これで、すべての
Claude Code セッションを一度に見られる:どれがあなたの応答を待っているか、どれが作業中か、どれが待機中か、どれが予期せず止まって再開できるか。
読むのは `/fw-fleet`、`npx flightwake fleet`、下部ゲージの `⛔` 欄、そして下の「セッションファイルの契約」を通じてほかのツール(Orca)。

**状態。** `working`(ターン実行中、または手動の `/compact`)、`blocked`(応答待ち)、`idle`(ターンの合間)、`ended`(セッション終了。理由つき)。
`blocked` になるのは次の場合だけ:

- **許可ダイアログ**が出ている——対話セッションで、下層の誰も答えなかった `PermissionRequest`(どの settings hook も決定を返さなかった)。
  `ask` の判定だけでは数えない:auto モード、分類器、headless の決定者では誰にも尋ねないので、blocked と表示されることはない。
- または、メインループで **`AskUserQuestion` か `ExitPlanMode`** の呼び出しが進行中。サブエージェントの質問は数えない。
  サブエージェントの許可ダイアログは数える(`(サブエージェント)` と表示)。

**置き場所。** `<base>/sessions/<セッション ID>.json`。`FLIGHTWAKE_HOME` が**絶対**パスなら `<base>` はそれ、そうでなければ
`$HOME/.flightwake`(Windows では `%USERPROFILE%\.flightwake`)。空または相対の `FLIGHTWAKE_HOME` は無視する。
`npx flightwake init --mod`、`update --mod`、setup の「更新してアドオンを追加」は `<base>/sessions` がなければモード `0700` で作る(既存のフォルダーの権限は変えず、symlink なら拒否する)。
mod が先にフォルダーを作った場合、ファイルの権限は umask に従う(通常 `0644`)。

**いつ書くか。** 状態が変わったとき、`/clear` や `/resume` の後に新しい ID を引き継いだとき、そして 30 秒ごとのハートビート。
ふつうのツール呼び出し、プロンプト、コマンドでは書かない——およそ 1 ターンに 2 回、ダイアログ 1 つに 2 回、30 秒に 1 回。毎回ファイル全体を書き直す。

**決して書かないもの。** プロンプトの本文、Bash コマンドの本文、質問・選択肢・プランの本文、URL、クエリ、パターン、repo の外のパス、
許可の `tool_input`、MCP のメッセージ、git の remote や branch、モデル、コスト。ファイルにあるのは ID、repo のパス、
ツール名、Edit / Write / MultiEdit / Read / NotebookEdit の repo 相対パス、時刻とカウンター、それに(mod 0.3.0 以降)コンテキスト使用率、席のロール ID、flightwake のバージョンだけ。

**何も書かない場合。** どれも `/fw-mod` にアイドルの理由として表示され、ほかの機能には影響しない:

- `-p` / SDK 実行(誰も応答できず、CI がフォルダーをあふれさせる)
- ホームフォルダーがない(`HOME` / `USERPROFILE` 未設定、または絶対パスでない)
- `<base>` が**このセッションの repo の中**にある——`FLIGHTWAKE_HOME` を repo の外の絶対パスに設定すること(書き込みのたびに再確認する。repo のルートは `/cd` や worktree の移動に追従する)。実際のパスでも判定するので、`<base>` の上に repo へ通じるリンクがあっても該当する。実際のパスが得られないときは何も書かない
- `<base>` が flightwake の記録フォルダー(`STATE.md` がある:`$HOME` にインストールされた repo、または `FLIGHTWAKE_HOME` がどこかの repo の `.flightwake`)、または**どこかの git リポジトリか flightwake のルートの中**(`<base>` かその上のフォルダーに `.git` か `.flightwake/STATE.md`。実際のパスでも確認)——ファイルがそのリポジトリに現れ、その `uninstall --purge` も届いてしまう。答えの得られない確認は該当とみなす
- `<base>`、`sessions` フォルダー、またはファイルがシンボリックリンク(経由して書き込まない。ハートビートのたびに再確認する。答えが得られなければリンクとみなす)
- ファイルがあるが flightwake のセッションファイルではない(触れない。ハートビートのたびに再確認するので、あとから置かれたものも上書きしない)
- セッション ID がファイル名にできない
- 書き込みに失敗した——次の変化で再試行

`.flightwake/STATE.md` のないフォルダーでは、ファイルもタイマーもコマンドもヒントもない。

**スイッチ。** `fleet`、既定でオン。同じ `pluginConfigs` のキーに `"fleet": false` と書けばオフ。すでに書かれたファイルはその後
応答なしになる(再開候補として 1 回示されることがある)——`npx flightwake fleet --prune` で削除できる。

### `/fw-fleet`

読み取り専用。直近 7 日のセッションファイル(新しい順に最大 200)を、応答待ち(長く待っている順)、作業中、待機、応答なし、終了の順に並べる
(終了は最大 10 行)。`/fw-fleet all` で 30 日に広げる。ハートビートが 120 秒より古いセッションは**応答なし**と表示し、作業中や応答待ちとは
決して表示しない。読めないファイル(書き込み中か破損)はフッターで数える。不明な形式、時計が 60 秒より進んでいる、1 つのセッションを
2 つのプロセスが使っている場合は「不明」と表示する。再開コマンドが付くのは、応答なしのセッションと、終了したセッション(通常の終了、ログアウト、
予期しない終了のどれでも。ただし `/clear` や `/resume` の後は除く——そのプロセスは別の ID で続いている)のうち、少なくとも 1 ターン実行し、
transcript がまだあるもの。(1 回だけの「再開のヒント」はもっと狭く、予期しない停止だけが対象。)

```
## /fw-fleet

**稼働 3 · ⛔ 応答待ち 1 · 再開可能 1** — ~/.flightwake/sessions(直近 7 日)

| 状態 | セッション | repo | 経過 | 詳細 |
|---|---|---|---:|---|
| ⛔ 応答待ち | `3f9a2c1e` | api | 2m | 許可確認 · Bash |
| ● 作業中 | `8b21d0aa`(このセッション) | flightwake | 12s | Edit src/a.ts |
| ● 作業中 | `c0ffee12` | orca ⎇ feat-x | 1m | Read(サブエージェント) |
| ○ 待機 | `77aa0b3c` | web | 5m | 回答済み |
| ◌ 応答なし | `1234abcd` | flightwake | 2h | ハートビートなし(作業中だった)——クラッシュかスリープ? · `claude --resume 1234abcd-…` |
| – 終了 | `deadbeef` | web | 1d | 終了 |

古い終了済みファイル 2 件は非表示——`/fw-fleet all` で 30 日分を表示。
読み取り専用:/fw-fleet は何も変更しません。7 日より古い終了/応答なしのファイルは `npx flightwake fleet --prune` で削除。
```

`orca ⎇ feat-x` は repo `orca` の worktree(`feat-x`)。そのセッションが別のフォルダーで起動されていた場合、再開コマンドの前に
`cd '…' && ` が付く——`claude --resume` はセッションを起動した場所で実行する必要がある。

### `npx flightwake fleet`

同じ一覧をターミナルで見る。どのフォルダーからでも実行できる(repo は不要。git は実行しない)。`--prune` 以外は読み取り専用。

```
npx flightwake fleet                     # テキスト。応答待ちが先頭
npx flightwake fleet --json              # ツール向けの JSON オブジェクト 1 つ(ファイルと同じく追加のみ)
npx flightwake fleet --all               # 30 日。終了の行数に上限なし
npx flightwake fleet --root=/abs/path    # repo かメインの作業ツリーがそのパスのセッションだけ
npx flightwake fleet --prune [--days=N] [--dry-run]   # N 日(既定 7)より古い終了/応答なしのファイルを削除
```

`--lang=` で言語を選ぶ(なければ現在のフォルダーの flightwake の言語、それもなければ英語)。再開コマンドには必ず `cd '…' && ` が付く。
`--prune` が触れるのは、フォルダー直下の通常の `<id>.json` ファイルだけ:終了から N 日を超えた終了ファイル、最後のハートビートから N 日を超えた
応答なしのファイル、またはそれより前に最後に更新された、自分たちの書きかけのファイル(`{"schema":"flightwake.session/` で始まる)か知らないバージョンの
`flightwake.session/` ファイル。自分たちのものでないファイル(ほかの JSON)、直近 120 秒に更新されたファイル、フォルダー自体は決して削除しない。
フォルダーが repo か記録フォルダーの中にあるときは拒否する(exit 1、何も削除しない)。
`<base>/sessions` の中身が削除されるのは**これだけ**:`npx flightwake uninstall` も `--purge` もこのフォルダーを残し(すべての repo で共有)、
その旨を 1 行表示する。

### 下部ゲージの欄

ほかのセッションが 2 秒以上応答待ちで、そのハートビートが生きているとき、下部ゲージ(`statusline.mjs`)はブランド名のすぐ後ろ(2 番目、
切り詰められても残る位置)に赤い欄を出す:1 つなら `⛔ api が応答待ち`(repo 名、最大 16 文字)、複数なら `⛔ 2 件が応答待ち`。
自分のセッションは数えない。読むのは直近 120 秒に更新されたファイルだけで、書き込みもネットワークもない。

### 再開のヒント

新しいセッションの開始時(リロード、`/clear`、`/resume` では出ない)に最大 1 回:**同じ repo フォルダー**のセッションが直近 7 日以内に
予期せず止まり——ハートビートが途絶えた(クラッシュ、`kill -9`、電源断)か、理由 `other` で終了した——少なくとも 1 ターン実行し、
transcript がまだあり、その後そのフォルダーで誰も新しいセッションを始めていなければ、toast を 1 つ出してそのセッションを示し、`/fw-fleet` を案内する(完全な再開コマンドはそこに出る。toast は約 40 桁でセッション ID が収まらない):

```
flightwake: セッション 1234abcd が 2h 前に予期せず停止(作業中)——再開コマンドは /fw-fleet
```

ふつうの `/exit`、`/clear`、`/resume`、ログアウトでは決して出ない。「1 回だけ」はファイル自体で判断する:そのフォルダーで新しいセッションが
始まっていれば候補は外れる——ほかに何も保存しない。

### セッションファイルの契約

スキーマ `flightwake.session/1`。JSON(`JSON.stringify(rec, null, 2)` と改行 1 つ)、UTF-8、通常 1.2 KB 未満、書き込みのたびに全体を書き直す。
すべてのフィールドが常にある。`null` は不明を意味し、見せかけの 0 は使わない。時刻は epoch ミリ秒。

| フィールド | 意味 |
|---|---|
| `schema` | `"flightwake.session/1"` |
| `mod` | 書き込んだ mod のバージョン |
| `sessionId` | セッション ID。ファイルのベース名と同じ |
| `instance` | プロセスごとの書き込み元トークン(ホットリロードでも変わらない) |
| `state` | `working` / `blocked` / `idle` / `ended` |
| `why` | 直前の状態変化の機械向けの理由(たとえば `permission-dialog`、`turn.complete:answer`、`adopt:clear`)。ハートビートでは変えない |
| `stateSince`、`seq`、`heartbeatAt`、`heartbeatMs` | 状態が最後に変わった時刻、書き込みごとに +1、最後の書き込み時刻(終了後は固定)、`30000` |
| `startedAt` | このプロセスがこの ID を引き継いだ時刻 |
| `root`、`repoRoot`、`launchCwd` | セッションの作業ルート(`/cd` や worktree の移動に追従)、メインの作業ツリーまたは null、セッションを起動した場所——`claude --resume` はここで実行する |
| `lang`、`surface` | 表示言語、`terminal` など、または null |
| `blocked` | null、または `{kind: permission / question / plan, tool, target, agent, since}`——`state` が `blocked` のときだけ null でない。最も古い待ちを示す |
| `activity` | null、または `{tool, target, agent, at}`——最後に始まったツール呼び出し |
| `inFlight`、`turns` | いま実行中のツール呼び出しの数、これまでのターン数 |
| `lastTurn` | null、または最後のメインループのターンの `{reason, at, durationMs}` |
| `ended` | null、または `{reason, at, stateAtEnd}`——`reason` は Claude Code のセッション終了理由か `id-changed` |
| `resume` | `{id, resumable}`——`resumable` は少なくとも 1 ターン実行したこと |
| `transcript` | transcript のパス、または null |
| `parent` | null、または `{sessionId, via: clear / resume / fork / id-changed}`——同じプロセスでこのセッションが置き換えたセッション |
| `contested` | 2 つのプロセスが 1 つの ID を使っているとき true |
| `host` | 環境変数が設定されているキーだけ:`orcaTerminal`(`ORCA_TERMINAL_HANDLE`)、`orcaWorkspace`(`ORCA_WORKSPACE_ID`)、`tmuxPane`(`TMUX_PANE`) |
| `context` | mod 0.3.0+:null、または `{percent}`——直近のターンまたはハートビート時のコンテキスト使用率(丸めた値) |
| `role` | mod 0.3.0+:このフォルダーの Claude の席のロール id(`.claude/CLAUDE.md` / `CLAUDE.md` の roles ブロックから)、または null |
| `fwVersion` | mod 0.3.0+:repo の指示ファイルのマーカーにある flightwake のバージョン(`0.16.0`)、または null |

`target` は repo 内の Edit / Write / MultiEdit / Read / NotebookEdit の repo 相対パス、それ以外は null。サブエージェントの呼び出しなら `agent` は true。

読み手のルール:

- v1 は**追加のみ**。知らないフィールドは無視し、ないフィールドは null とみなし、知らない `state` や `kind` は `unknown` にする。
  知らないメジャーバージョンは ID とハートビートを添えて `unknown` と表示する。
- 解析の失敗は一時的なもの(書き込み途中):その回はそのファイルを飛ばし、最後に正しく読めた値を使い続ける。
- **応答なし:** `now − heartbeatAt > max(4 × clamp(heartbeatMs, 5000, 600000), 90000)`、`heartbeatMs` がなければ 30000(現在は 120 秒)。応答なしのファイルは作業中や応答待ちにならない。
  `contested: true`、または `heartbeatAt` が 60 秒より先の時刻なら `unknown`。
- 応答待ちの**通知**は `now − blocked.since ≥ 2000` のときだけ出し、`${sessionId}:${blocked.since}` で重複を除く。
- 削除は `npx flightwake fleet --prune` だけ。

Orca などのツール向けの指針:

- フォルダーを監視し(`fs.watch`、200 ms のデバウンス、5 秒のポーリングを予備に)、変わったファイルだけを読み直す。ポーリングのたびに
  `npx flightwake fleet --json` を起動しないこと。
- ファイルとペインの対応は `host.orcaTerminal` で取り、なければ `root` / `launchCwd`(`heartbeatAt` が最新のものを優先)。
- `/clear` をまたぐときは `parent.sessionId` をたどる。
- 再開ボタン:`launchCwd` で `claude --resume ${resume.id}` を実行する。

#### trip ファイル

`<base>/trips/<session id>.json`。書くのは `tripwire`(`fleet` ではない)で、`<base>`、ファイル名の規則、書き込みの防護はセッションファイルと同じ。
セッション ID ごとに 1 ファイル、エントリに一致したツール呼び出しのたびに全体を書き直す(`JSON.stringify(t, null, 2)` と改行 1 つ):

```json
{
  "v": 1,
  "sessionId": "<id>",
  "repo": "/abs/path/of/the/repo",
  "updated": "2026-10-26T08:00:00.000Z",
  "trips": { "<trap name>": { "n": 3, "first": "<ISO>", "last": "<ISO>" } }
}
```

- `repo` は最後に一致したときのセッションのルート(絶対パス、Claude Code が報告するとおり)、`updated` は最後に一致した時刻。時刻は ISO 8601、UTC。
- `trips` のキーはエントリの `name`(内容を直したエントリも同じ名前で数え続ける)。`n` ≥ 1 は、そのエントリに一致したツール呼び出しの回数で、ヒントを出したかどうかは問わない。1 回の呼び出しは、エントリごとに 1 回だけ数える。
- そのパスにあるファイルが `v: 1` で同じ `sessionId` のものでなければ、決して上書きしない。mod が trip ファイルを削除することはない。

## 下部ゲージと帯を一緒に使う

`setup` では両者は同じ一覧の別々の行(1 行目がゲージ、2 行目が mod)なので、片方だけ・両方・どちらもなしを選べる。両方をインストールした場合、終了時のメッセージはこう説明する:下部ゲージは health / STATE の遅れ / コンテキスト使用率を表示し、
プロンプト上の帯は、ゲージが有効な間はそれと同じ項目を隠して静かにし、コンテキストが逼迫したときに toast を 1 回出すだけ。
mod を選んでもゲージが外れることはない。
ゲージがない場合は、帯が常に表示されてゲージの代わりをする(インストーラーの終了時のメッセージもそう説明する)。

インストール後にインストーラーが表示すること:読み込まれたかどうかと各機能の状態は Claude Code で `/fw-mod` を実行して確認できること;Claude Code 2.1.287 以降が必要;repo のルートから始め、信頼プロンプトを承認すること;
この repo で Claude Code を開いたままなら、そのセッションからは mod が見えないので、終了して repo のルートから起動し直すこと(mod は Claude Code の起動時に読み込まれる);
ロールガードを自分でオンにする方法(上の `pluginConfigs` のキー、または `/config`);そしてそれがセキュリティ境界ではないこと。

## 制限——必ず読むこと

- **`/fw-log` の「pass」が意味するのは、**直接呼び出された、認識できるテストランナーが、認識できる形で実行され、0 を返した、ということだけ。
  テストが実際には走らなくなる設定——設定ファイルや環境の中のもの(たとえば pytest.ini の `addopts`、テストを飛ばすビルドプロファイル)——は見えず、
  テストが何を検査しているかを保証するものでもない。証明できないものは、pass ではなく「unknown」として終了コードとともに記録される。
- **ロールガードはセキュリティ境界ではない。** Bash とそのほかのツールは検査されず、サブ agent も検査されず、
  禁止パスの symlink などの別名も捕まえられない。
- **`/fw-log` のシェル由来の変更一覧は不完全なことがある。** コマンドから推定したもので、リポジトリ内の出力リダイレクト(`>`、`>>`)の対象と、`cp`、`mv`、`rm`、`tee`、`sed -i` だけが対象。スクリプト、ほかのプログラム、git による書き込みは見えない。「agent が変更したファイル」の一覧は、Edit / Write / NotebookEdit が報告したものだけのまま。
- **確認できたパスだけを載せる——漏れはありうるが、誤りは載せない。** 各コマンドはそれぞれのオプション文法で読むので、オプションの値(sed の `-e` / `-f` のスクリプト、cp の `-t` / `-S`)はパスとして扱わない。相対パスは作業ディレクトリが確定している間だけ解決する(最初、または先頭の `cd dir &&` の後)。それ以外の `cd` の後は推測しない。repo の外のパスは載せない。さらに、実行後に git が repo 内で変更ありと示した候補だけを載せる。git repo でなければ何も載せない。(落とし穴の検知線は意図的に逆の取捨をしている:ヒントにすぎないので出しすぎる方を選ぶ。記録は記録なので漏らす方を選ぶ。)
- **ほかのコマンドと連結して実行されたテストコマンドは「unknown」として記録される**(たとえば `echo … && npm test 2>&1; echo exit=$?`——見えるのは連結全体の終了コードだけ)。agent には session ごとに 1 回、そのツール結果に注記が付く:そのような実行は pass の証拠にならない。証拠が必要なときは、テストコマンドを単独で 1 回実行すること。注記は事実を述べるだけで、何もブロックしない。
- tripwire が作業ディレクトリを確定できないとき(たとえば `||` の後の `cd`、サブシェルの中)は、候補ディレクトリごとに照合する(最大 16 個。超えるとパスの末尾部分での照合に切り替える)ので、必要以上にヒントが出ることがある。
- **セッション状態の報告:許可ダイアログが長く残ることがある。** 「ダイアログに応答した」ことを示すイベントがない:承認した後、ツールは同じ呼び出しの中で
  実行されるので、ツールが終わるまでセッションは `blocked` のまま。ターミナルでは、ツールの進行表示が描かれた時点で解除される。MCP ツールと
  WebFetch は終わるまで応答待ちのまま。「経過」欄は `blocked.since` から数え、表示は「許可確認」であって「ダイアログ表示中」ではない。
- **デスクトップアプリ、VS Code、Remote Control でのセッション状態の報告は未検証。** そこで許可のイベントが発生しなければ、ダイアログは作業中と
  表示される——見逃しであって、誤報ではない。
- **セッション状態の報告と同期されたホームフォルダー:** 別のマシンの稼働中のセッションも稼働中に見える(ファイルにホスト名はない)。
- **1 つのセッション ID を 2 つのプロセスが使う**(たとえば 2 つのターミナルでそれぞれ `claude --resume <id>`)と「不明」と表示される。
  片方が終了してもう片方が動いていると、もう片方の次のハートビートまで最大 30 秒、ファイルは終了と表示する。
- **セッションの途中で `fleet` をオフにする**と、ファイルは応答なしになり、再開候補として 1 回示されることがある。`npx flightwake fleet --prune` で削除できる。
- **ポリシー面。** `fleet` があると、hooks モジュールは `fs.write`、`fs.list`、6 つの環境変数の読み取り(`FLIGHTWAKE_HOME`、`HOME`、
  `USERPROFILE`、`ORCA_TERMINAL_HANDLE`、`ORCA_WORKSPACE_ID`、`TMUX_PANE`)を使う。`tripwire` があると、trip ファイルのために `fs.write` とそのうち最初の 3 つの環境変数を使う。`panel` があると、さらに `ORCA_CLI_BIN_DIR` を読み、
  Orca の中で `orca` CLI を実行する(上の「サイドパネル」を参照)。ファイルを書く、またはプロセスを実行するプラグインを拒否する管理ポリシーは、
  この機能だけでなく mod **全体**を拒否する。
- **Fleet パネルの状態は一部が推測。** fleet ファイルのないエージェント(Codex、ほかの CLI、mod のない Claude Code)の作業中 / 待機中 / 応答待ちは、タブのタイトルと直近の出力から読むので、最大 10 秒遅れることがあり、エージェントがタイトルの形式を変えると外れることもある。**締め**は送る前に取り直して確かめるが、使うのは同じ推測でしかない。
- Claude Code 専用。2.1.287 以降、承認済みのフォルダー信頼プロンプト、repo のルートからの開始が必要。
- 実際の Claude Code の session で 1 回検証した(最初の 5 つの機能が効いた)。**まだ実際の session で検証していないもの**:
  `spend` 機能、再起動後の session の再開、compaction 後の挙動、80% の toast、デスクトップ / VS Code での見た目、`/config` にオプションが並ぶかどうか(ドキュメントにはそう書かれている)、そして `fleet` 機能全体(リリース前に、
  ダイアログ、auto モード、AskUserQuestion、`/clear`、`/exit`、`kill -9` の各場面を実際の session で確認する必要がある)。
